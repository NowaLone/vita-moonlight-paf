# План диагностического оверлея стрима

Дата: 2026-10-19. Статус: исходная реализация в `codex/stream-diagnostics`;
сборка и проверка на Vita не выполнены.
Исследован основной проект `691e7fa` и локальный moonlight-common-c
`2d984f4b0dfab5ea2cff0f262abe1a056946a7c1`.
Критерии выполнения хранятся в [ROADMAP.md](../ROADMAP.md).

Обновление после проверки пользователем: исходный 18-строчный оверлей оказался
слишком большим. Текущий компактный вариант ограничен шестью строками и панелью
660×136: режим/битрейт, FPS, доступный RTT, пропуски, среднее время вызова декодера
и очереди PAF, host latency при её наличии. Недоступные строки скрываются;
служебные подробности, звук, max-времена и постоянные `N/A` убраны из отображения.
Сбор статистики сохранён. Этот вариант ещё не проверен на Vita; исходные описания
18-строчного формата и его проверок ниже относятся к предыдущей реализации.

В логе после зависания подтверждён отказ создания потока остановки (`EAGAIN=11`).
Вместо создания нового потока на stop текущий поток запуска теперь живёт всю
сессию, опрашивает RTT и сам выполняет очистку по запросу. Отдельный RTT worker
и его condition wait удалены. Callback прекращения соединения сохраняет владение
cleanup до `LiStopConnection()`, затем отправляется событие остановки. Исправлено
также повторное добавление persistent PAF callbacks в пути вывода кадров и
отложенного освобождения буферов. Это исправления исходников, не подтверждённое
объяснение первоначального зависания и не результат повторного прогона на Vita.

## Реализовано в исходниках

Добавлены модуль `stream_stats.c`, снимки через ConnectionService/backend/API,
замеры video/audio callbacks и CXML-оверлей (сокращён с 18 до 6 строк). Сохранён key `show_fps`,
изменено только видимое название настройки. Обновление UI выполняется раз в секунду
независимо от новых кадров; RTT опрашивает владелец сессии до освобождения
транспорта. Старые поколения не могут записывать
данные в новую сессию. Декодирование и pacer drops учитываются одним событием,
чтобы граница окна не разносила числитель и знаменатель процента пропусков.

Из варианта ниже выбран достоверный `Decoder call time`; полного сопоставления
отложенных изображений с decode unit не добавлено. PAF queue wait начинается
на входе в очередь и включает ожидание её mutex; CPU-submit заканчивается после
установки поверхности/обновления её геометрии, до форматирования UI. Prequeue
включает Vblank/crop; соответствующая подробная строка удалена из компактного UI.
Аудио собирает параметры Opus, время вызовов decode/output и ошибки, без утверждений о задержке
до динамиков. RTP/FEC snapshot API, дополнительная синхронизация common-c и
GPU/display completion в эту реализацию не входят. Недоступные показатели
отмечены `N/A` или не выводятся. Необязательные покадровые замеры выключены
вместе с настройкой. Ниже сохранены определения и план проверки; это не отчёт
об успешной работе на устройстве.

Выполненные проверки без сборки: `git diff --check`, разбор XML интерфейса,
проверка привязок всех `style_text`, сохранения key/default настройки, разбор
C-модуля и публичных структур через `pycparser`. Проверено соответствие 40
printf-аргументов формату оверлея и размещение 18 строк в буфере 2304 байта
через системный `snprintf` с тестовыми значениями, а также количество аргументов
в 72 объявлениях/определениях/вызовах API статистики и видеомоста. Это проверки исходников и
форматирования, не исполнение Vita-кода и не проверка математических расчётов
на реальном потоке. Сборка, производительность, числовые результаты и читаемость
на экране остаются открытыми. После сокращения проверены XML и отсутствие второстепенных
строк; для исправления lifecycle проверены грамматика C-подмножества кода сессии
(без проверки SDK-типов), число регистраций PAF и интерпретированы реальные тела
обработчиков состояния: idle stop, отмена pending-запуска, повторный stop, ошибка
хоста и завершение. Это проверки без сборки и без исполнения Vita API.

## Цель и состояние до реализации

Заменить существующий вывод `fps: текущее / целевое` диагностикой по образцу
скриншота пользователя из Moonlight Qt. Сначала добавить все достоверно измеримые
показатели видеотракта; затем дополнительные показатели транспорта и звука.

До реализации `vita_video_note_presented()` считал кадры до crop и вызова
`moonlight_video_present()`. Далее `Stream::QueueFrame()` хранит один ожидающий
кадр: следующий может заменить его до обработки PAF. Поэтому прежний FPS —
частота отправки кадров в сторону UI, а не подтверждённая частота показа на экране.
Значение обновлялось по числу кадров за интервал не короче секунды без деления
на фактическую длительность. Новый модуль делит число кадров на прошедшее время.

## Какие строки со скриншота можно вывести

1. **Video stream: разрешение, FPS, codec.** Брать размер, формат и целевую частоту
   из callback `vita_video_setup()`, фактический FPS считать отдельно. Показывать
   размер входного стрима, а не размер поверхности после масштабирования/crop.
   Сейчас клиент запрашивает только H.264; HEVC на скриншоте не означает поддержку
   HEVC на Vita. Сохранять фактически согласованный формат из callback.

2. **Incoming frame rate.** Считать полные `DECODE_UNIT`, пришедшие в
   `vita_video_submit()`, до попытки декодирования. Это FPS собранных кадров,
   а не пакетов и не целевая частота из настроек.

3. **Decoding frame rate.** Считать реально полученные выходные изображения
   `sceAvcdecDecode()`, включая те, которые затем отбросил pacer.
   Не приравнивать успешный вызов декодера без выходного изображения к кадру.

4. **Rendering frame rate → PAF submit FPS.** Считать успешные установки
   поверхности в `Stream::PresentFrame()`. Честное название на первом этапе —
   `PAF submit FPS`: `SetTexture()` не подтверждает физический показ кадра.
   Отдельно считать замены ожидающего кадра в `QueueFrame()`.

5. **Host processing latency min/max/avg.** Поле
   `DECODE_UNIT.frameHostProcessingLatency` уже доступно; единица — 0,1 мс.
   Нулевые значения означают отсутствие измерения/неприменимость, их исключать
   из всех трёх агрегатов. При отсутствии валидных значений выводить `N/A`.
   Это сообщённое хостом время обработки кадра, не полный input-to-display lag.

6. **Frames dropped by network.** Оценивать пропуски последовательных
   `frameNumber`, как в Qt: `missing / (received + missing) × 100%`.
   Назвать `Frames missing before decoder`: эта оценка включает недоставленные
   декодеру кадры при восстановлении потока, а не только потерянные UDP-пакеты.
   Инициализировать базу первым кадром; учитывать переход счётчика через границу,
   повтор/старый номер и новую сессию без отрицательных или огромных процентов.

7. **Frames dropped due to network jitter → Local drops.** Разделить на
   `Pacer drops` и `PAF pending replacements`, при необходимости дать проценты
   с явными знаменателями: выходные кадры декодера и поставленные в PAF очередь
   кадры соответственно. Текущий `vita_video_pacer_should_drop()` проверяет
   минимальный временной интервал; он не устанавливает причину «сетевой джиттер».
   Отдельную точную оценку сетевого джиттера не обещать без модели времени прихода.

8. **Average network latency.** `LiGetEstimatedRttInfo()` возвращает ENet RTT и
   его variation в мс. Выводить `Network RTT / variation`; это полный путь туда
   и обратно по управляющему каналу, а не односторонняя задержка видеопакетов.
   Это оценка ENet, не собственное среднее за окно оверлея. При отказе API — `N/A`.

9. **Average decoding time.** Основной замер: от `enqueueTimeUs` до готового
   декодированного изображения; дополнительно можно измерить сам вызов
   `sceAvcdecDecode()`. Первый включает подготовку входных данных и ожидание
   декодера, второй показывает длительность API-вызова. При отложенном выходе
   сопоставлять изображение с исходным кадром; не использовать метку следующего
   decode unit. Если надёжное сопоставление недоступно, показать только отдельно
   названный `Decoder call time`.

10. **Average frame queue delay.** Передавать временные метки и идентификатор
    вместе с кадром; измерять ожидание между `QueueFrame()` и началом обработки
    соответствующего кадра в `PresentFrame()`. Дополнительно измерить путь от
    готовности декодера до очереди: ожидание Vblank и crop не должны потеряться
    или случайно попасть сразу в две метрики. Это Vita/PAF-этапы, не копия очереди Qt.

11. **Average rendering time including V-sync.** Сейчас доступно время CPU
    на подготовку поверхности и `SetTexture()`, отдельно — явное ожидание
    `sceDisplayWaitVblankStart()`. Показывать `PAF submit CPU time` и
    `Explicit Vblank wait`, когда ожидание включено. Полное время рендера PAF/GPU,
    композиции и физического показа требует отдельного подтверждённого механизма
    завершения презентации. До этого не подписывать CPU-замер как полный render/V-sync.

## Дополнительная доступная диагностика

- **Битрейт:** заданный из настроек и фактический по сумме `fullLength` за время
  окна. Второй подписать `Video payload Mbps`: он не включает FEC, заголовки,
  управляющий канал и звук и не равен полной загрузке сети.
- **Сборка кадра:** `enqueueTimeUs - receiveTimeUs`, среднее/максимум в мс.
  Это время от первого пакета до готового кадра, не время доставки от ПК.
- **Декодер:** число ошибок, возвратов `DR_NEED_IDR`, полученных IDR и случаев
  без выходного изображения. Возврат `DR_NEED_IDR` не называть количеством
  фактически отправленных запросов IDR.
- **Путь вывода:** режим Fit/Center Region, размер/stride выходной поверхности,
  состояние pacer и явного Vblank wait. Параметры стрима и вывода разделять.
- **Аудио:** фактические параметры Opus, ошибки декодирования и длительность
  вызовов decode/output; блокирующий `sceAudioOutOutput()` не равен полной
  задержке звука до динамиков.
- **RTP audio:** `LiGetRTPAudioStats()` содержит заполняемые счётчики FEC,
  восстановлений, ошибок и нарушения порядка. Перед отображением каждого поля
  проверить точную единицу: например, FEC failure не обязательно один пакет.
  Копировать согласованный снимок через безопасную границу потоков.
- **RTP video:** API `LiGetRTPVideoStats()` есть, но в локальном `RtpVideoQueue.c`
  обновляются только `packetCountVideo` и `packetCountFec`, причём по ожидаемому
  числу data/parity пакетов блока. Это не счётчики реально принятых пакетов.
  Остальные поля здесь не заполняются. Полноценные video packet loss/FEC recovery
  потребуют отдельного узкого изменения common-c; до него выводить их как
  недоступные или не показывать, а не выдавать нули за отсутствие потерь.

`LiGetPendingVideoFrames()` и `LiGetPendingAudioDuration()` не описывают наши
локальные очереди при `CAPABILITY_DIRECT_SUBMIT`, который включён у обоих
рендереров. Не использовать их нулевые значения как доказательство отсутствия
задержки. Полный input-to-photon lag, односторонняя сетевая задержка, точная
частота физического показа и реальное время GPU сейчас достоверно не измеряются.

## Порядок реализации

1. **Сбор и модель данных.** Добавить небольшой модуль статистики в
   `src/moonlight/` с C-совместимыми функциями учёта и структурой снимка.
   Хранить счётчики/суммы/минимумы/максимумы и признаки валидности в памяти;
   использовать одну шкалу `LiGetMicroseconds()`. В common-c на Vita она имеет
   собственную начальную точку: нельзя вычитать `enqueueTimeUs` из текущего
   `sceKernelGetSystemTimeWide()` без приведения часов.
2. **Замеры видеотракта.** Ввести приём/декодирование/ошибки/пропуски/битрейт
   в renderer; протянуть метаданные до очереди PAF. В UI оставить только отметки
   событий передачи поверхности и заполнение текста. Сохранять границу
   API → adapter/backend → services → MoonlightApp для чтения снимка страницей;
   не добавлять прямое управление транспортом или legacy globals из UI.
3. **Согласованные снимки.** Защитить обмен счётчиками между decoder/audio/UI;
   учитывать 64-битные значения на 32-битной Vita. Не удерживать lock во время
   decode, Vblank, `SetTexture()` или блокирующего audio output. Получать RTT/RTP
   только в допустимом окне жизни соединения, с защитой от одновременного teardown.
   Сбрасывать все данные, номера кадров и окна при новой сессии. Отложенные
   callbacks старой сессии не должны менять статистику новой.
4. **Оверлей и настройка.** Заменить подпись `Display streaming FPS` на
   `Display stream statistics`, сохранив существующий AppSettings key `show_fps`
   и его значение. В CXML создать отдельный связанный многострочный text style:
   верхний левый угол, компактные подписи, читаемый текст на тёмной полупрозрачной
   подложке. Размер шрифта и высоту блока подобрать на 960×544 и проверить на Vita;
   не переносить размеры ПК вслепую. Сначала строки из основного списка, затем
   короткие сгруппированные дополнения. При нехватке места согласовать расширенный
   режим вместо уменьшения шрифта до нечитаемого. Обновить `docs/UI.md` вместе
   с реализацией UI.
5. **Частота обновления.** Собирать числовые события без форматирования строк
   на каждом кадре, обновлять текст примерно раз в секунду по двум последним
   секундным окнам. FPS = количество / реальное время; среднее время = сумма /
   число валидных образцов. Отдельная задача обновления UI должна работать и
   при остановке прихода кадров, чтобы FPS падал к нулю, а старые latency-значения
   помечались устаревшими. При выключенной настройке отключить необязательные
   дорогие замеры/обновления. Никаких файловых логов и покадровой печати.
6. **Расширение.** После проверки основного оверлея добавить аудиостатистику;
   отдельно решить, нужны ли изменения vendored common-c для реальных
   видеопакетных/FEC-счётчиков. Новые API/аппаратные исследования ради недоступного
   времени GPU не должны блокировать полезные показатели первого этапа.

## Проверка и критерии приёмки

Проверить расчёты на заданных последовательностях: нерегулярные окна, нулевые
знаменатели, отсутствующая host latency/RTT, потери и восстановление, переполнение
номера кадра, замена ожидающего кадра, остановка поступления и новая сессия.
Для математической части подойдут некомпилируемые скриптовые проверки; сборки
приложения/ресурсов выполняет maintainer.

На Vita сравнить одинаковые сцены с оверлеем и без него: 30/60 FPS, доступные
разрешения, Fit/crop, pacer/Vblank on/off, обычная и ухудшенная сеть, Quick Actions,
stop/reconnect и разрыв соединения. Оверлей должен помещаться, сохранять читаемость,
сбрасываться при reconnect и не вызывать заметного ухудшения плавности/звука.
Зафиксировать результаты, не объявляя source review аппаратной проверкой.
